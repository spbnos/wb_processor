## 🎯 ЦЕЛЬ ТРЕКА

Построить **полную операционную систему управления магазином(ами) WB** —
не просто аналитику (это уже есть в `wb_processor`), а замкнутый контур:

```
ДАННЫЕ (WB API + отчёты) → CANONICAL REGISTRY → DATA WAREHOUSE
   → ДАШБОРДЫ → AI-АНАЛИЗ → АВТОМАТИЗАЦИИ (правила) → ДЕЙСТВИЯ (через API обратно в WB)
```

### Жёсткое ограничение (от пользователя, обязательно)
**Запрещено придумывать**: отчёты, API-методы, поля данных, бизнес-процессы WB.
Если что-то не подтверждено официальной документацией dev.wildberries.ru —
помечать как **«ГИПОТЕЗА — требует проверки в Swagger»**, не выдавать за факт.

### Источник истины
- `https://dev.wildberries.ru/openapi/api-information` (и подкатегории: Content,
  Prices and Discounts, Marketplace, Statistics, Supplies, Analytics, Promotion,
  Feedbacks and Questions, Reports, Documents, Returns, Tariffs, Seller Info, Chat)
- Уже выгруженное в репозитории: `WB_API/wb_registry.json`, `WB_API/refs.json`,
  `WB_API/wb_products_openapi.json`, `WB_API/endpoints.txt` — **50 эндпоинтов**,
  подтверждено Шагом 1.1: это **100% полная спецификация `02-products.yaml`**
  ("Работа с товарами") официального API, не узкое подмножество.
- Вторичный источник для быстрой навигации по структуре всего API (не панацея,
  финальная сверка полей — всегда по dev.wildberries.ru):
  `github.com/eslazarev/wildberries-sdk` — автогенерируемое SDK, синхронизируется
  с офиц. OpenAPI несколько раз в неделю (см. его CHANGELOG.md).
- При сомнении в поле/методе — **искать в вебе** официальную страницу
  dev.wildberries.ru, не утверждать из памяти.

### Фундамент (не дублировать, расширять)
Этот трек **строится поверх** существующего `wb_processor`:

### ШАГ 1.3 — Сущность «Остатки/Склады/Поставки» ✅ ВЫПОЛНЕН (2026-06-23)

**Источник**: `WB_API/wb_products_openapi.json` (полный документ с `components/schemas`,
первоисточник со Swagger) для FBS-методов из `02-products.yaml`; web_search по
`eslazarev/wildberries-sdk` и `Dakword/WBSeller` для методов `07-orders-fbw.yaml`
(этой спецификации нет в нашей выгрузке вообще — собрано из вторичных источников,
**требует точечной проверки на dev.wildberries.ru перед написанием кода**).

#### 1.3.А — Остатки FBS: `/api/v3/stocks/{warehouseId}` (есть в `02-products.yaml`, ✅ выгружено)

Ключевая находка — **операционная единица здесь `chrtId` (ID размера), не `nmID`
и не баркод**:
- `POST .../stocks/{warehouseId}` (запрос остатков) — body: `{chrtIds: [int]}`
- `PUT .../stocks/{warehouseId}` (обновить) — body: `{stocks: [{chrtId, amount}]}`,
  max 1000 позиций за запрос, `amount` ≤ 100000
- `DELETE .../stocks/{warehouseId}` — body: `{chrtIds: [int]}`

**Это подтверждает находку Шага 1.2** (`sizes[].chrtID`) — `chrtId` это сквозной
идентификатор, который связывает карточку (Content API), остатки FBS и (см. ниже)
сборочные заданий FBS. **У нас в системе `chrtId` не сохраняется вообще ни в одном
парсере** — это пробел, который заблокирует прямую интеграцию с FBS-остатками,
если она понадобится.

#### 1.3.Б — Склады продавца (FBS): `/api/v3/warehouses` (✅ выгружено)

Схема `Warehouse` (из `components/schemas`, точная, с офиц. enum-описаниями):

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | ID склада продавца |
| `name` | string | Название (свободный текст) |
| `officeId` | integer | ID склада WB, к которому привязан склад продавца |
| `cargoType` | enum(1,2,3) | 1=МГТ (малогабаритный), 2=СГТ (сверхгабаритный), 3=КГТ+ (крупногабаритный) |
| `deliveryType` | enum(1,2,3,5,6) | 1=FBS, 2=DBS, 3=DBW, 5=самовывоз (C&C), 6=экспресс-DBS |
| `isDeleting` | boolean | Признак удаления (склад скоро пропадёт из списка) |

**Важно для понимания доменной модели**: это **не склады WB**, а склады/точки
отгрузки САМОГО ПРОДАВЦА, через которые идёт FBS/DBS/DBW/самовывоз. Склады WB
(куда едет FBO) — отдельная сущность, см. 1.3.В.
`GET /api/v3/offices` — это именно склады WB (куда продавец может привязать
свой склад через `officeId`), также есть в нашей выгрузке.

#### 1.3.В — Поставки FBW (на склады WB): `07-orders-fbw.yaml` (❌ НЕ выгружено — собрано из вторичных источников, нужна проверка)

По данным `wildberries-sdk` (см. полный список выше) и `Dakword/WBSeller`,
спецификация покрывает два разных версионных пространства методов:

**`/api/v1/...` — информация для планирования поставок:**
- `GET /api/v1/acceptance/coefficients` — **коэффициенты приёмки** по складам
  (ключевое для расчёта: платность/доступность приёмки меняется по складам и
  датам в зависимости от загрузки — прямо нужно для Шага 1.6/Этапа SCOS-3
  юнит-экономики, в нашем текущем калькуляторе `WBCommissions.tsx` этого
  параметра нет, используется фиксированный тариф)
- `POST /api/v1/acceptance/options` — опции приёмки (какие типы упаковки/коробов
  принимает конкретный склад)
- `GET /api/v1/warehouses` — список складов WB **для целей FBW** (отличается от
  `/api/v3/offices` по версии пространства имён, требует проверки — возможно
  один и тот же справочник под разным путём, гипотеза, не факт)
- `POST/GET /api/v1/supplies`, `GET /api/v1/supplies/{ID}/goods`,
  `GET /api/v1/supplies/{ID}/package` — список/детали/товары/упаковка поставки
- `GET /api/v1/transit-tariffs` — транзитные тарифы между регионами

**`/api/v3/...` — управление поставками (более новая версия):**
- `GET/POST /api/v3/supplies`, `GET/DELETE /api/v3/supplies/{supplyId}`,
  `GET .../supplies/{supplyId}/barcode` (QR-код поставки),
  `PATCH .../supplies/{supplyId}/deliver` (передать в доставку)
- `GET /api/v3/passes/offices`, `PUT/DELETE /api/v3/passes/{passId}` — **пропуска
  на склады** (для физического проезда машины с поставкой)

**ГИПОТЕЗА, требует проверки**: судя по нумерации (`v1` для информации,
`v3` для управления поставками + отдельно `marketplace/v3` для привязки
сборочных заданий к поставке), это вся одна спецификация FBW/FBS-поставок,
но точное разделение `07-orders-fbw.yaml` vs `03-orders-fbs.yaml` по этим
методам **не подтверждено напрямую** — `wildberries-sdk` показывает общий
список без явной привязки метод→файл-спецификация. Уточнить на Шаге 1.4
при разборе заказов FBS, так как `/api/v3/supplies` тесно связаны со
сборочными заданиями (`orders`), которые точно относятся к `03-orders-fbs.yaml`.

#### Сопоставление с нашими файловыми парсерами

#### 1.4.А — Statistics API: простая хронологическая выгрузка (❌ полностью новая область)

Базовый URL отличается от Content/Prices API: `statistics-api.wildberries.ru`
(отдельный хост — отдельный токен категории "Статистика").

**`GET /api/v1/supplier/orders`** — заказы:
- Гарантия хранения данных: **90 дней** от даты заказа. Обновление каждые 30 мин.
- 1 строка = 1 заказ = 1 товарная позиция (не агрегат по заказу-корзине)
- Лимит на один ответ: **80 000 строк**, нужна пагинация через `lastChangeDate`
  последней строки предыдущего ответа как новый `dateFrom`
- Лимит запросов: **1 запрос в минуту** на аккаунт продавца (жёсткий rate-limit)
- Ключевые поля (по найденному примеру ответа): `supplierArticle`, `nmId`,
  `barcode`, `category`, `subject`, `brand`, `techSize`, `incomeID`, `isSupply`,
  `isRealization`, `totalPrice`, `discountPercent`, `spp` (скидка постоянного
  покупателя), `finishedPrice`, `priceWithDisc`, `isCancel`, `cancelDate`,
  `orderType`, `sticker`, `gNumber`, **`srid`** (уникальный ID заказа — "1 строка
  = 1 заказ/товар", основной идентификатор для связки с другими отчётами)

**`GET /api/v1/supplier/sales`** — продажи и возвраты (тот же общий формат):
- Аналогичные лимиты (90 дней хранения, 30 мин обновление, 80 000 строк/ответ,
  1 запрос/мин)
- Дополнительные поля относительно `orders`: `paymentSaleAmount`, `forPay`
  (сумма к выплате — это **уже агрегированная по транзакции величина**, отличается
  от `ppvz_for_pay` в финансовом отчёте ниже — гипотеза: разные стадии расчёта,
  не подтверждено точно), `saleID` (отдельный ID продажи, отличный от `srid` заказа)
- **Один и тот же эндпойнт отдаёт и продажи, и возвраты** — различаются по
  знаку/типу операции внутри потока строк, отдельного метода "только возвраты"
  через Statistics API не обнаружено (см. ниже про Reports API для возвратов)

#### 1.4.В — Возвраты: отдельный отчёт vs `/api/v1/supplier/sales`

Найдено явное подтверждение, что у WB есть генерируемый асинхронный отчёт

не обнаружено — возвраты, видимо, идут в общем потоке `/api/v1/supplier/sales`

#### 1.4.Г — Sales Funnel (воронка продаж) — относится к `11-analytics.yaml`, не к заказам/продажам

Важное разграничение, обнаруженное попутно: метод

относится "Stock report" и "Search queries" с **доступом только по подписке

### ШАГ 1.5 — Сущность «Реклама» (`08-promotion.yaml`) ✅ ВЫПОЛНЕН (2026-06-23)

**Источник**: web_search по `dev.wildberries.ru/en/openapi/promotion`,
`dev.wildberries.ru/en/forum/topics/*` (официальный community-форум разработчиков
WB API — там разработчики WB и продавцы напрямую обсуждают баги/изменения,
очень ценный, но **неофициальный по статусу** источник), digest изменений за
сентябрь 2025.

#### 🚨 ВАЖНЫЙ РИСК (зафиксировать в Этап 10 — Roadmap/риски)

Реклама — **самая нестабильная часть WB API из всех исследованных до сих пор**.
Прямые подтверждения:
1. **Баг в проде на момент поиска**: новый метод `GET /adv/v3/fullstats`
   возвращает нули в `views`/`sum`/`clicks` для части кампаний, при этом в
   личном кабинете данные корректные. Обсуждение на форуме без ответа от WB.
2. **Жёсткий breaking change с дедлайном**: ставки переводятся из рублей в
   копейки в новых версиях методов; старые версии (рубли) отключаются
   **02 февраля** (год не указан явно в сниппете — требует уточнения при
   реализации, не позже). WB предупреждает заранее, но миграция обязательна.
3. **Известная архитектурная проблема производительности**: по словам
   продавца на форуме — обновление ставок по 3000 кампаниям при текущих
   лимитах (20 запросов/мин) занимает **~5 часов** при текущей структуре API
   "1 кампания = 1 запрос". WB пока не предоставил bulk-метод.
4. **Метод нормальных запросов (`/adv/v0/normquery/*`) выдаёт 403** даже при
   правильно подключённой категории токена "Маркетинг/Продвижение" — ответ
   техподдержки WB не получен автором вопроса за 2+ дня.

**Вывод для Roadmap**: модуль "AI Рекламщик" (Этап 6) и любая автоматизация
ставок (Этап 7) **не должна проектироваться как MVP-приоритет** именно из-за
документированной нестабильности этого конкретного API на момент исследования.
Рекомендация: закладывать **retry/circuit-breaker с самого начала**, не строить
автоматику ставок без ручного approval-шага (человек подтверждает изменение
ставки, а не AI меняет её сам), минимум до стабилизации API со стороны WB.

#### Подтверждённые методы (с конкретными полями/семантикой)

**Управление кампаниями**:
- `POST /adv/v2/seacat/save-ad` — создать кампанию аукционного типа (Auction, type=9)
- Создание автоматической кампании (отдельный метод, тип "automatic")
- Параметры при создании: `payment_type` (новое поле, добавлено недавно — `cpm` или
  `cpc`), лимиты: **до 50 кампаний** в тестовом окружении (сэндбоксе)
- Статусы кампании: 4=готова к запуску, 9=активна(?), 11=на паузе,
  -1=удалена (удаляется физически через 3 минуты)
- Запуск кампании: можно запускать только в статусах 4 и 11; для статуса 11
  обязателен пополненный бюджет
- Завершение кампании: доступно для статусов 4, 9, 11
- Автоудаление: кампания удаляется через **30 дней** после последнего изменения

**Ставки**:
- `GET /adv/v0/normquery/get-bids` — ставки по кластерам поисковых фраз (новый метод)
- `GET /adv/v0/normquery/stats` — статистика по кластерам поисковых фраз
- `PATCH /api/advert/v1/bids` — изменение ставок (новая версия, ставки в копейках)
- `POST /api/advert/v1/bids/min` — минимальные ставки для карточек товаров
- Структура ответа по ставкам (подтверждённый пример):
  ```
  bids: [{advert_type, payment_type: "cpm"|"cpc", type: "search"|"recommendation"|"combined"|null, value}]
  ```
  `advert_type` — числовой тип кампании (8=автоматическая, 9=аукцион — подтверждено
  по тексту "статистика формируется только для типов 8 и 9")
- Изменённая ставка применяется в кампании **в течение 3 минут**
- Если новая ставка ниже допустимого минимума → код **422** ("Rate size not changed")

**Статистика**:
- `GET /adv/v3/fullstats?ids={advertId}&beginDate=&endDate=` — детальная статистика
  по дням/площадкам/товарам (подтверждённый реальный пример ответа):
  ```
  {advertId, atbs, canceled, clicks, cpc, cr, ctr,
   days: [{date, apps: [{appType, atbs, canceled, clicks, cpc, cr, ctr,
                          nms: [{nmId, name, orders, shks, sum, sum_price, views}],
                          orders, shks, sum, sum_price, views}],
           atbs, canceled, clicks, cpc, cr, ctr, orders, shks, sum, sum_price, views}],
   orders, shks, sum, sum_price, views}
  ```
  Поля: `atbs`=добавления в корзину, `shks`=штук продано, `sum`=затраты,
  `sum_price`=сумма продаж, остальное самоочевидно (views/clicks/cpc/cr/ctr)
- `GET /adv/v1/upd` — история затрат (это, вероятно, прямой аналог нашего
  файлового отчёта "История затрат", который парсит `ad_cost_history`!)

**Бюджет**:
- `GET /adv/v1/balance` — баланс кампании, **включая промо-бонусы** (новое,
  добавлено сентябрь 2025): `{balance, cashbacks: [{sum, percent}]}` —
  `percent` — макс. доля бюджета, которую можно покрыть бонусами
- `POST /adv/v1/budget/deposit` — пополнение бюджета (поддерживает оплату бонусами)
- История пополнений — отдельный метод (не задокументирован детально в найденном)

**Справочники**:
- `GET /adv/v1/supplier/subjects` — предметы, доступные для рекламных кампаний
- `POST /adv/v2/supplier/nms` — карточки товаров, доступные для кампаний
- Метод "нет доступных категорий для РК" — известное сообщение об ошибке при
  попытке создать кампанию без подходящих карточек

#### Выводы Шага 1.5

1. **`ad_cost_history` ≈ `/adv/v1/upd`** по названию метода — вероятный, но не
   подтверждённый по полям аналог. Это вторая (после `daily_detailed`≈
   `reportDetailByPeriod` из Шага 1.4) находка "наш файл = вероятный аналог
   конкретного API", но здесь уровень уверенности ниже — нужна точечная
   проверка структуры ответа перед реализацией.
2. **Реклама — зона повышенного риска для автоматизации.** Документированные
   баги, breaking changes с дедлайнами, известные проблемы производительности.
   Любой код для Этапа 6/7 в этой зоне должен закладывать защитные механизмы
   с первого дня, не как "доделаем потом".
3. **Доступ к управлению ставками требует отдельной категории токена**
   ("Маркетинг/Продвижение" отдельно от "Контент"/"Статистика") — это值
   нужно явно отразить в Canonical Registry (Этап 2) как атрибут категории
   API-доступа, не все организации/токены будут иметь доступ к этой области.
4. Полная сверка реальных полей `/adv/v1/upd` против нашего `ad_cost_history`
   переносится в "довыяснить" список (вместе с возвратами из Шага 1.4) —
   не блокирует переход к Шагу 1.6.
